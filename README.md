# Real-Time Data Quality KPI Pipeline

Streaming data quality monitoring for healthcare event feeds (claims, eligibility,
pharmacy). Events flow through Kafka; a Python consumer validates every event as it
arrives and computes data quality KPIs - **completeness**, **error rate**, **freshness**
and **volume** - per feed, so a feed that starts going bad is caught in minutes instead
of at the next batch load.

> All events are synthetic, generated by `src/dq_stream/events.py`.

## Architecture

```
  producer.py                Kafka                      consumer.py
 ┌────────────┐      ┌──────────────────┐      ┌──────────────────────────────┐
 │ synthetic  │      │ dq.claims        │      │ decode → validate_event()    │
 │ events     │ ───> │ dq.eligibility   │ ───> │   missing fields → completeness
 │ + error /  │      │ dq.pharmacy      │      │   bad values     → error rate │
 │ late inject│      └──────────────────┘      │   event_time lag → freshness │
 └────────────┘                                └──────────────────────────────┘
                                                     │
                                                     ▼
                                   WindowAggregator (60s tumbling, per feed)
                                                     │
                                                     ▼
                                   AlertEngine: thresholds + baseline drift ──→ log / Slack
                                                     │
                                                     ▼
                       KpiStore: SQLite dq_kpi_window + dq_alert, CSV export  →  Power BI
```

| Piece | File | What it does |
|---|---|---|
| Feed config | `config/feeds.yaml` | Topic, required fields, field rules, freshness SLA, alert thresholds per feed |
| Event generator | `src/dq_stream/events.py` | Random claims / eligibility / pharmacy events with adjustable error and late rates |
| Validator | `src/dq_stream/validator.py` | Per-event checks; returns missing fields and rule errors, never raises on bad data |
| Kafka I/O | `src/dq_stream/kafka_io.py` | Thin confluent-kafka producer/consumer wrapper (manual commits) |
| KPI windows | `src/dq_stream/kpi.py` | Event-time tumbling windows per feed with a watermark for late data |
| KPI store | `src/dq_stream/sink.py` | SQLite table `dq_kpi_window` (upserts) + CSV export for Power BI |
| Alerts | `src/dq_stream/alerts.py` | Threshold (CRITICAL) and baseline-drift (WARN) alerts with FIRING / RESOLVED state |
| Simulator | `src/dq_stream/simulate.py` | Same pipeline without Kafka, with injectable incidents |

## Feed config

Each feed is described in YAML - adding a feed or tightening a rule is a config change:

```yaml
pharmacy:
  topic: dq.pharmacy
  freshness_sla_s: 60
  required: [rx_id, member_id, ndc_code, quantity, fill_date]
  rules:
    quantity: {type: number, min: 1, max: 1000}
    ndc_code: {pattern: "^[0-9]{5}-[0-9]{4}-[0-9]{2}$"}
    fill_date: {type: date, not_future: true}
  thresholds:
    max_error_rate_pct: 1.0
```

Supported field rules: `type: number` (+ `min` / `max`), `type: date` (+ `not_future`),
`allowed: [...]`, `pattern: <regex>`.

## KPIs

One row per feed per window (default 60 seconds), keyed by **event time**:

| KPI | Meaning |
|---|---|
| `events` | Events that belong to the window (a sudden drop = upstream problem) |
| `completeness_pct` | % of events with every required field present |
| `error_rate_pct` | % of events breaking at least one field rule |
| `p50_lag_s` / `p95_lag_s` / `max_lag_s` | Processing time minus event time |
| `sla_breach_pct` | % of events later than the feed's `freshness_sla_s` |
| `dropped_late` | Events that arrived after their window had closed, counted on the window they arrived in |
| `top_missing` / `top_error` | The field behind most of the problems - where to look first |

A window closes when the feed's watermark (newest event time seen − 120s allowed
lateness) passes its end, so moderately late events still land in the right minute
while a big backlog shows up as `dropped_late` instead of silently rewriting history.

## Alerts

Each closed window is checked per metric (completeness, error rate, p95 lag, volume):

| Check | Severity | Example |
|---|---|---|
| Threshold from `feeds.yaml` | CRITICAL | pharmacy error rate 6.7%, limit 1% |
| Drift from the feed's own baseline (z-score over the last 15 healthy windows) | WARN | claims p95 lag 112s, normally ~4s - still under the 300s limit, but something changed |
| Volume vs. recent average | CRITICAL | eligibility 25 events/min, normally ~120 |

To keep it quiet enough to trust:

- a metric must be bad for **2 windows in a row** before it fires
- each incident produces one `FIRING` and one `RESOLVED`, not an alert per minute
- only healthy windows feed the baseline, so a long incident doesn't become "normal"
- spread floors stop 1-2 bad records out of ~120 from looking like drift

Tested on 10 simulated hours of normal traffic: **0 alerts**; every injected incident
fires within 2 minutes. Alerts go to the log, the `dq_alert` table / `dq_alert.csv`, and
Slack if `SLACK_WEBHOOK_URL` is set (see `.env.example`). A failing webhook is logged and
never stops the consumer.

## Simulate an incident (no Kafka needed)

```bash
python simulate.py --minutes 12 \
    --error-spike pharmacy:4:7:0.15 \
    --volume-drop eligibility:2:4:0.2 \
    --late-burst claims:8:10:0.4
```

```
window feed         events complete%  error%  p95 lag   sla% dropped  top problem
08:02  eligibility      23     100.0     0.0     3.95    0.0       0             <- volume drop
08:04  pharmacy        121     92.56    6.61     3.66   2.48       0  fill_date  <- error spike
08:06  claims          133     100.0    0.75   121.31   5.26       0  claim_amount
08:08  claims           68     100.0     0.0     3.97    0.0      33             <- late burst
08:09  claims           82     100.0     0.0     3.99    0.0      34
...
36 KPI rows -> output/dq_kpi.db, output/dq_kpi_window.csv, output/dq_alert.csv
```

Format is `feed:start_minute:end_minute:value`; flags can be repeated. The run also prints
the alerts it raised:

```
Alerts (8):
  08:05  FIRING   CRITICAL pharmacy completeness=97.46, expected >= 98.0%
  08:05  FIRING   CRITICAL pharmacy error_rate=5.93, expected <= 1.0%
  08:06  FIRING   WARN     claims p95_lag=121.31, expected ~3.84 for this feed (z=+23.5)
  08:07  RESOLVED CRITICAL pharmacy completeness back to normal (100.0)
  08:07  RESOLVED CRITICAL pharmacy error_rate back to normal (0.0)
  08:08  RESOLVED WARN     claims p95_lag back to normal (3.97)
  08:09  FIRING   WARN     claims volume=82, expected ~123.00 for this feed (z=-3.3)
  08:10  RESOLVED WARN     claims volume back to normal (121)
```

The eligibility drop at 08:02 isn't flagged here: volume and drift checks need 5 minutes
of history first, and that incident starts in minute 2. In the 60-minute run in
`samples/` the same kind of drop is caught.

## Quick start

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

docker compose up -d               # Kafka on localhost:9092, Kafka UI on http://localhost:8080

# terminal 1 - consume, validate, write KPI windows to output/dq_kpi.db
python consumer.py --csv

# terminal 2 - send a healthy feed, then a bad one
python producer.py --feed claims --rate 20 --seconds 60
python producer.py --feed pharmacy --rate 20 --seconds 60 --error-rate 0.10
```

No Kafka handy? Print events instead:

```bash
python producer.py --feed claims --count 5 --dry-run --error-rate 0.5
```

Tests don't need Kafka either:

```bash
python -m pytest -q
```
